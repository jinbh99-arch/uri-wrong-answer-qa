# QA40 G15 — 서명 검증 인증 주체 ↔ 보호자 RLS 연동 (합성 검증판)

**2026-11-08 / 실서비스 계정·클라우드 사용 없음 / 승인 상태: 미완료**

## 실제 구현과 검증 범위

- `scripts/qa40-oidc-resolver.mjs`: SHA-256 서명을 사용하는 **합성 RSA 공개키(JWKS)** 로 JWT의 서명, 신뢰 발급자(issuer), API 수신 대상(audience), 발급시간(iat), 만료시간(exp), 사용 시작(nbf), 키 식별자(kid)를 확인.
- 토큰 서명·만료·사용처가 부정확하거나 공개키가 일치하지 않으면 상세 토큰 내용을 노출하지 않고 `AUTHENTICATION_REJECTED`로 거부.
- 확인된 `issuer + subject`의 불변 식별자로부터 일방향 해시의 사용자 키를 파생. **브라우저가 전달한 가족 ID로 권한을 승인하지 않음.**
- `tests/qa40-oidc-postgres.mjs`: 실제 PostgreSQL 16에 있는 **검증 완료 보호자 역할**을 함께 조회해 가상 기록을 읽고 조건부 저장. 합성 JWT가 진짜 암호학적 서명에 통과하더라도 **보호자 DB 권한이 없으면 자료 접근 금지**, 권한 철회 후에는 JWT가 유효하더라도 차단하는지 확인.

## 아직 운영용 인증이 아닌 이유

이 구현은 `QA40_SYNTHETIC_JWKS_ONLY=1`을 요구하며, 시험에서 생성한 공개키 집합을 코드로 주입하는 **합성 JWKS 전용 검증기**입니다. 인증 공급자(OIDC) 선택, 실제 권한 범위와 토큰 종류 확인, 공급자 JWKS HTTPS 신뢰·키 교체·키 폐기·JWT 취소/재로그인, 토큰의 공개 웹앱 보관방법, 보호자·법정대리인 관계 확인과 계정 복구는 **미연결**입니다.

운영에서는 실제 API용 검증 가능한 접근 토큰을 사용하고, 로그인 화면에서 임의로 제출한 이메일·가족 ID 또는 서명 없는 JWT를 신뢰하지 않아야 합니다. **ID Token을 그대로 API Access Token이라고 간주하지 않습니다.** 공급자에서 발행한 적절한 API audience/scopes/토큰 타입 및 키 회전 정책을 외부 문서와 실제 발급 결과로 검증해야 합니다.

추가로 JWT는 사용자가 누구인지 증명하는 한 요소일 뿐입니다. 법정대리인 증빙·동의·보유/삭제 권한은 **독립적인 보호자 권한 테이블과 검증 절차**가 있어야 하며, 합성 키·가상 guardian 테이블에 권한 레코드가 있다고 실사용 보호자 확인을 마쳤다고 주장할 수 없습니다.

## 실제 출시 전 운영 검토 항목

1. **인증 공급자 결정:** 토큰 발급자, API Audience, RS256/ES256 알고리즘, 키 조회/회전, 가입·인증 복구, 다중 기기 로그아웃·강제 철회 및 법정대리인 확인 근거.
2. **비공개 API 분리:** 공개 GitHub Pages에서 운영 DB 접속권한을 전달하거나 `qa39_app` 비밀번호를 넣지 않을 것. HTTPS API 서버에서만 토큰을 검증하고 DB 세션을 설정.
3. **RLS 방어 깊이:** 직접 DB 네트워크 접근 금지, 인가된 서버 최소 권한, 매 요청 거래 범위 `SET LOCAL` 및 별도 관리계정 권한 분리. DB 세션 변수 자체는 인증이 아님.
4. **민감자료·사진:** 저장 지역, 암호화, 객체 사진 저장/다운로드 접근권한, 백업·복구/삭제·권리 행사, 개인정보 처리 위탁 및 감사를 실제 서비스 검증 후 확정.
5. **실기기·실계정 검수:** 실제 Android/iOS 2기기에서 보호자 인증, 오답/사진 원본, 수정·재풀이·삭제/철회, 오프라인·동기화 충돌 확인.
6. **출시 승인:** 관련 개인정보/보호자 동의 법률 검토·운영 사고대응과 결합하고, 새 G15 관련 게이트의 실제 증빙을 독립 승인받기 전 운영 데이터 수집 금지.
